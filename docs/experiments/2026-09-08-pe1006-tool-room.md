# Does a tool-call room with a standing account beat a fenced one?

**Date** 2026-09-08
**Status** Recorded
**Code** `cargo run --release -p tinyhivemind --example desk` at `ed060e5`, with
`--desk crates/tinyhivemind/examples/desk/desks/pe1006.txt --window 12 --rounds 8
--max-turns 40 --chair-every 6 --no-memory`, one `opencode run … -m ladder/deepseek`
per turn against `deepseek-v4-pro`.
**Spec** [`thoughts-and-channels.md`](../specs/thoughts-and-channels.md),
[`seat-continuity.md`](../specs/seat-continuity.md)
**Sample** one run (run 28), compared against runs 26 and 27 on the same task,
the same desk file, and the same model. n=1 per arm: read the direction, not the
magnitude.

## The question, written before the numbers

Run 26 and run 27 both failed the same way. A seat is a fresh process each turn,
so it opened its turn by re-reading the workspace to find out where it was: run
27's first turn spent **15 of 19** tool calls on `read`, and run 26 spent **27 of
53** across three turns. Neither run computed the answer.

Two changes were made for run 28: a seat speaks by calling a tool rather than by
emitting a `<<<POST … POST>>>` fence, and everything older than the live window
is folded into one standing account of the room. The question was whether either
changes the re-reading, and whether the desk gets further.

## What happened

Run 28 solved the problem.

```text
Psi(10^18) mod 101001001 = 62418970
```

Verified three ways before being written down here: the desk's own
`run_final.py` reproduced it in 0.48s from a cold shell; its `verify_final.py`
re-checked `cross k=0..44` and `Psi(1..30)` against brute force; and a
brute-force script written independently from the problem statement confirms the
anchors `Psi(3)=20302`, `Psi(10)=10699667` and the `k+1` factor count. Runs 26
and 27 produced no answer at all.

| | run 26 | run 27 | run 28 |
| --- | --- | --- | --- |
| turns | 3 | 1 | 12 |
| `read` calls | 27 of 53 (51%) | 15 of 19 (79%) | **4 of 133 (3%)** |
| tokens (turn lines) | 288,227 | 98,447 | 603,835 |
| answer | none | none | **62418970, signed off** |

Per-turn reads in run 28, in order: `0/36, 3/40, 0/18, 0/4, 0/4, 1/7, 0/4, 0/4,
0/4, 0/5, 0/3, 0/4`. The three reads on turn 2 are a seat opening `NOTES.md` and
`factors.py` for the first time, which is the notebook working rather than
failing.

Wall clock was 100.7 minutes for 23 rows, **4.4 minutes per message**, against
run 27's 19.4.

## What actually caused it

Not the standing account. **The account never folded once**, and the run does not
test it. With `--window 12` the policy is `keep_live: 12, fold_after: 20`, so a
fold needs `head > 32` rows and the desk closed at 23. No `room account:` line
appears in the log. Anything below is the notebook, the tool-call room, and the
landing phase — not compaction.

What did carry the run is the workspace surviving the process boundary. Turn 1
ran out of its 40-minute budget having posted nothing; the landing phase asked it
to write down what it had, and it produced `factors.py` and `NOTES.md`. Turn 2
then *ran `factors.py`* rather than re-deriving it, closed the `Cross(n,k)` bug
turn 1 had left open, and posted the answer. That hand-off is the whole result.

The hand-offs were also honest. Turn 1 said `Cross(n,k)` "still has a bug I could
not close this turn"; turn 2 asked `@checker` to "independently verify and sign
off" rather than declaring victory; turn 3 re-derived the anchors with its own
brute code and rejected a binary-read trap that would have given `Psi(3)=46`.

## Two defects this run found

**Seats write outside the workspace.** Turn 1 wrote `/tmp/fp.py` and
`/tmp/break2.py`. Nothing was lost, because the landing recovered it — but
recovery cost a 40-minute timeout, and the fix is one sentence in the prompt
saying files must be relative and under the workspace. Obligation 4 in the desk
README was about the agent CLI resolving writes against its own project root;
this is the same failure reached by a different route, a seat freely choosing an
absolute path.

**The room had no way to say it was finished.** The answer was signed off on turn
3. Turns 4–12 are `@lead` being nudged by the chair once per remaining round and
replying "the desk is finished, not stalled" nine times — by turn 12 it was
counting the loops ("Ninth loop, same result"). That is **9 of 12 turns and
~154k tokens** spent restating a delivered answer, because the chair's nudge
fires on `rounds` alone and no tool existed to contradict it. Note it is not a
model failure: the seat diagnosed the situation correctly every time and had no
way to act on it.

## What changed because of it

- `desk_close(message)` was added to the room's tool surface: a seat says one
  last thing and reports the work finished, and the host appends the row and then
  closes. It is still a *request* — the host appends and decides — so
  one-message-one-turn is untouched.
- The prompt now says files must be written under the workspace as relative
  paths, and that a `/tmp` write is gone when the process ends.
- Neither change was exercised live. They are covered by unit tests only, and
  the next run on this task is what tests them.

## What this does not show

- **n=1 per arm.** Three runs, one configuration each, one model. The read-count
  gap is large enough to be worth acting on and is not a measurement.
- **The account is untested.** Criterion 7 of the spec stays open on the half
  that concerns compaction. A run that folds needs more than 32 rows, or a
  smaller `fold_after`, and the desk now closes earlier rather than later.
- **Run 28 spent more tokens than either baseline** (603,835 against 288,227 and
  98,447). It also finished the problem, which neither baseline did, so the
  comparison is between a solved run and two unsolved ones rather than between
  two solutions.
