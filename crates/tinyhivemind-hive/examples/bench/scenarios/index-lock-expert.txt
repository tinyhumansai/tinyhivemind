# A hidden-profile incident with a named specialist, first design.
#
# Two designs were tried and discarded before this one.
#
# Design 1 made the truth the obvious first move: the on-call channel's own
# instinct — "a migration just shipped, roll it back" — was also the correct
# answer. Every member would reach for it unprompted and the matched-budget
# vote could not lose. Discarded for the same reason the first two checkout-503
# drafts were: an arm that cannot lose is not a control.
#
# Design 2 put every fact a room would need behind one member — the database
# engineer held both the index's growth number and the fact that ruled out
# rolling back. That member could read its own private brief and the shared
# task and reach `reindex` alone, deletion-check or no. A scenario whose
# "expert" can solve it solo is not a hidden profile, it is a member with the
# right answer already in hand.
#
# This design instead gives the database engineer one number and nothing to do
# with it alone, and gives every other member exactly one fact that rules out
# one wrong move and points at nothing. The truth stands only once every
# elimination has been made and the number has been read alongside it.

task: Since last night's schema migration, p99 write latency on the orders table has climbed from 80ms to 4s and lock wait timeout errors in the application log are rising by the minute. The on-call channel's first read is that the migration broke something and should be rolled back. Ship exactly one change now, and say which.

truth: reindex
truth_expert: dba

[option rollback]
expert: planner
Roll last night's migration back in full.

[option reindex]
expert: dba
Drop the partial index on orders(status) and rebuild it against a predicate
that actually excludes most of the table.

[option addreplica]
Add two read replicas for the orders table and route reporting traffic to
them.

[option killqueries]
Add a two-second statement timeout and kill writers that exceed it.

[agent planner]
role: release manager, who owns what can and cannot be shipped
expert_on: migrations
knows: The migration that shipped last night is forward-only and additive. The partial index on orders(status) was created by a separate migration two hours after it, so rolling last night's migration back does not remove, or touch, that index at all.

[agent sre]
role: SRE on call, who owns the incident
expert_on: locks
knows: Every lock wait timeout in the log is on a write to the orders table. The two read replicas already in service report zero lock waits of any kind over the same window.

[agent analyst]
role: data analyst, who owns the traffic numbers
expert_on: traffic
knows: Requests per minute against the orders table are flat against the same hour last week, and unique sessions are flat too, so nothing is sending more writes than usual.

[agent scout]
role: application engineer, who owns the write path
expert_on: app-writes
knows: A two-second statement timeout was trialled against this exact symptom in staging last week. Queued writers simply retried and the timeout errors reappeared within seconds; the underlying wait never went away.

[agent dba]
role: database engineer, who owns the datastore
expert_on: indexes
knows: The partial index on orders(status) filters on status = 'pending'. That predicate matched 4% of the orders table's rows when the index was created six months ago. It matches 91% of the table's rows today.
